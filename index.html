What C is, and why Git uses it

C is a programming language from 1972. It's small, fast, and very close to how the computer actually works: you manage memory yourself, and values are just bytes at addresses. Operating systems (Linux), databases (PostgreSQL, SQLite) and Git are written in it.

Three things to know

  • It's compiled. A compiler (gcc or clang) turns .c files into a native program. There's no interactive prompt like Python's.
  • It's statically typed, but not very strict. Every variable has a type (int, char *, struct repository *), but C will happily convert between many of them. Warnings matter.
  • You manage memory. If you ask for memory with malloc, you must give it back with free. Forget, and you have a leak. Free twice, or use it after freeing, and the program may crash or behave strangely.

Headers, declarations and #include

C code is split in two. A header (.h) declares what exists: “there is a function called this, with these argument types”. A source file (.c) defines it: the actual code. Other files #include the header to use it.

Include guards

repository.h:1

#define REPOSITORY_H
…
#endif

#include literally pastes the file in. The guard makes sure that if a header is included twice, its contents only count once.

Forward declarations

This says “a struct with this name exists” without saying what's inside. That's enough to use a pointer to it (Level 3). It keeps headers from including each other in a huge web.

Git's include rule

Every .c file includes git-compat-util.h first. Then it includes exactly the headers it uses. A real patch removing the_repository from merge-blobs.c had to add #include "repository.h" and #include "read-cache-ll.h", because the code now looked inside struct repository and struct index_state directly.

Pointers: the one idea you must get

A pointer is a variable that holds the address of something else. Almost every function in Git takes pointers.

SyntaxMeaning
struct repository *rr holds the address of a repository
&x“the address of x”
*p“the thing p points at”

Following a chain

attr.c:782
buf = odb_read_object(istate->repo->objects, &oid, &type, &sz);

Read it left to right: from the index (istate), go to its repository (->repo), then to that repository's object database (->objects). struct index_state has a struct repository *repo field (read-cache-ll.h:189), which is why this works.

A C function can only return one value. To give back more, the caller passes addresses, and the function writes into them. Above, &type and &sz let odb_read_object fill in the object's type and size, while the return value is the data itself.

Level 4 strbuf.h · banned.h · git-compat-util.h

Strings and memory

A C string is a char *: the address of some bytes, ending in a zero byte ('\0'). There's no length stored anywhere and no automatic growth. That's why plain C string code is a common source of bugs.

Heap memory

char *copy = xstrdup("hello");   /* allocate and copy */
…
free(copy);                       /* give it back */

Git wraps malloc in xmalloc, xcalloc, xstrdup and friends. They never return NULL; they stop the program if memory runs out. Use them, not the raw versions.

strbuf: Git's growable string

strbuf.h:74
struct strbuf {
	size_t alloc;
	size_t len;
	char *buf;
};
#define STRBUF_INIT  { .buf = strbuf_slopbuf }
struct strbuf sb = STRBUF_INIT;
strbuf_addstr(&sb, "refs/heads/");
strbuf_addf(&sb, "%s", branch);
use(sb.buf);
strbuf_release(&sb);              /* frees the memory */

strbuf tracks the length and grows as needed. Almost all string building in Git goes through it.

Banned functions

banned.h makes strcpy, strcat, sprintf and a few others fail to compile, because they can write past the end of a buffer. If you reach for one, use strbuf or xsnprintf instead.

Freeing safely

#define FREE_AND_NULL(p) do { free(p); (p) = NULL; } while (0)

Setting the pointer to NULL after freeing means a second free does nothing, instead of corrupting memory.

Exercise

In plain C (no Git helpers), what's wrong with this?

char name[8];
strcpy(name, "refs/heads/main");
Answer

The string needs 16 bytes (15 characters plus the zero byte), but name holds 8. strcpy writes past the end and overwrites whatever is next in memory. That's exactly why Git bans it.

Errors, die() and goto cleanup

C has no exceptions. Git handles errors in two ways:

WayWhat happensWhen
return -1; or return error(_("…"));The function reports failure; the caller decides what to do. error() prints a message and returns -1.Library code that callers might recover from
die(_("…"));Prints a message and ends the whole processCommands that can't continue

die is declared NORETURN (git-compat-util.h:419), telling the compiler it never comes back. _("…") marks a message for translation.

This matters for libification. A library must never kill the program it's running inside. Part of the global-state work is changing library code from die() to returning an error the caller can handle.

goto for cleanup

merge-blobs.c:86 (merge_blobs)
if (fill_mmfile_blob(&f1, our) < 0)
	goto out_no_mmfile;
if (fill_mmfile_blob(&f2, their) < 0)
	goto out_free_f1;
…
out_free_f2_f1:
	free_mmfile(&f2);
out_free_f1:
	free_mmfile(&f1);
out_no_mmfile:
	return res;

goto jumps to a label. In Git it's used for one thing: when something fails halfway, jump to the right point in a list of cleanups so everything allocated so far is freed exactly once. The labels run top to bottom, so jumping to a later label skips cleanups for things not yet allocated.

Exercise

If the second fill_mmfile_blob fails, which buffers get freed, and why not f2?

Answer

It jumps to out_free_f1, so only f1 is freed with free_mmfile(&f1). The out_free_f2_f1 label above it is skipped. f2 was never filled, so there's nothing to free.

The switch at the heart of the project

repository.h:228
#ifdef USE_THE_REPOSITORY_VARIABLE
extern struct repository *the_repository;
#endif

A file can only see the_repository if it defines USE_THE_REPOSITORY_VARIABLE at the very top, before any include. environment.h hides its remaining global config variables behind the same switch. So:

  • A file with #define USE_THE_REPOSITORY_VARIABLE still depends on global state.
  • When you remove that line and the file still compiles, the file is free of it. The compiler proves it for you.
git grep -l "^#define USE_THE_REPOSITORY_VARIABLE" -- "*.c" | wc -l

In Git v2.56.0 that prints 248 files, 109 of them outside builtin/ and t/. Each one is a possible piece of work. The number shrinks as people send patches.

Other macros you'll meet

  • UNUSED: marks a parameter the function ignores, to silence a warning. cmd_hash_object(…, struct repository *repo UNUSED) takes a repository but doesn't use it yet.
  • ARRAY_SIZE(x): the number of elements in a fixed array.
  • do { … } while (0): wraps a multi-statement macro so it behaves like one statement after an if.

Scope, static and global variables

Where it's declaredLivesVisible to
Inside a functionUntil the function returnsThat function
static inside a functionThe whole program runThat function (keeps its value between calls)

The last two rows are global state: one copy for the whole process.

How the_repository is made

repository.c:30
/* The main repository */
static struct repository the_repo;
struct repository *the_repository = &the_repo;

One struct, private to this file, and one global pointer to it that any file can use through the extern declaration from Level 6.

Why globals are a problem

  • Hidden inputs. You can't tell from a function's parameters which repository it works on. It might quietly use the global.
  • Only one repository. A program that wants to work with two repositories at once (a submodule, or a server hosting thousands) can't, because the global points at just one.
  • Threads. Two threads changing the same global can corrupt it.

Function pointers, callbacks and void *data

In C you can pass a function to another function. Git uses this for “do something for each X” loops:

The void *data trick

static int prune_object(const struct object_id *oid, const char *path,
			 void *data)
{
	int *opts = data;      /* we know it's really an int * */
	…
}

The loop doesn't know what extra information your callback needs, so it carries a void *, a pointer to anything. You pass &opts in, and the callback turns it back into the right type.

This is also how callbacks can get a repository without using the global: pack the repository into a small struct, and pass that struct as data. You'll see this pattern in many global-state patches.

How a command runs

git.c:617

A table maps each command name to a function and some flags. RUN_SETUP means “find the repository first”. run_builtin() (git.c:470) then does roughly this:

if (run_setup & RUN_SETUP) {
	prefix = setup_git_directory(the_repository);
	no_repo = 0;
}
…
status = p->fn(argc, argv, prefix, no_repo ? NULL : repo);

Every builtin has the same signature:

builtin/hash-object.c:64
int cmd_hash_object(int argc,
		    const char **argv,
		    const char *prefix,
		    struct repository *repo UNUSED)
  • argc and argv: the number of words on the command line and the words themselves. const char ** is a pointer to a list of strings.
  • prefix: where you ran the command, relative to the top of the work tree.
  • repo: the repository, passed explicitly. It's NULL when there's no repository.

So builtins already receive the repository. A lot of the global-state work is threading this repo parameter down into the functions the builtin calls, so they stop using the_repository. Options are read with the parse-options API (parse-options.h), which is another Outreachy project's topic.

Level 10 the project itself

Patterns for removing global state

Read past patches before writing your own. Find them with:

git log --oneline --grep="the_repository" | head -30

You'll see subjects like “refspec: stop depending on `the_repository`”, “copy: drop dependency on `the_repository`” and “refs: remove remaining uses of `the_repository`”. Read the full messages and diffs with git show <hash>. Most follow one of these patterns:

Pattern 1: pass the repository in

Add a struct repository *r parameter, use r instead of the global, and update every caller. If a caller already has a repository (a parameter, istate->repo, a field of some struct), use that. This is what the preload-index commit in Level 3 does.

Pattern 2: move global config into the repository

Old code kept settings in globals filled from config. Newer code keeps them in struct repo_settings or struct repo_config_values and reads them through a function that takes the repository:

environment.c:141
int repo_trust_executable_bit(struct repository *repo)
{
	return repo->initialized
		? repo_config_values(repo)->trust_executable_bit
		: 1;
}

Notice the fallback: if the repository isn't set up yet, it returns the default (1). Edge cases like this are what reviewers look for.

Pattern 3: replace die() with a returned error

Where library code calls die(), change it to return error(…) and make callers handle the failure. Callers in builtin/ can still die if that's right for the command.

How to keep it reviewable

  • One small, focused change per commit. Changing a function's signature and updating its callers is one commit; a separate cleanup is another.
  • No change in behaviour. Say so in the commit message, and prove it: the existing tests must still pass.
  • Check lore before you start, in case someone is already working on the same file.

Look at the flag: -f is a file, -d a directory, -e "exists". ! test -f x usually means the path must be missing. If the code is inside an if (a condition, not a check), it may be correct as it is.

Hero every level in one path

Trace a repository from the command line to merge_blobs

Open the files side by side and follow the repository as it travels.

  1. You type git merge-tree …. main in git.c finds { "merge-tree", cmd_merge_tree, RUN_SETUP } in the command table (L0, L9).
  2. run_builtin() sees RUN_SETUP and calls setup_git_directory(the_repository), which fills in the global struct from repository.c (L7).
  3. It calls the builtin through a function pointer: p->fn(argc, argv, prefix, repo) (L8, L9).
  4. Inside builtin/merge-tree.c, which still defines USE_THE_REPOSITORY_VARIABLE (L6), the code calls merge_blobs(the_repository->index, path, base, our, their, size) (builtin/merge-tree.c:95).
  5. merge_blobs() (merge-blobs.c:62) gets the index as struct index_state *istate, a pointer (L3).
  6. It calls fill_mmfile_blob(&f1, our) (merge-blobs.c:86); the &f1 is an out-parameter (L3).
  7. fill_mmfile_blob reads the object with odb_read_object(the_repository->objects, …) (merge-blobs.c:15), because merge-blobs.c still defines USE_THE_REPOSITORY_VARIABLE in v2.56.0. If the read fails it returns -1, and the caller jumps to its cleanup label (L5).

Notice where the global still appears: in steps 4 and 7. Step 7 is library code, and the fix is Pattern 1: merge_blobs() already holds the index, and the index knows its repository (istate->repo), so that repository can be passed down to fill_mmfile_blob(), exactly like the preload-index commit. Step 4 is different: it's in a builtin, and in step 3 that repo parameter is NULL when there's no repository (no_repo ? NULL : repo, git.c:510). So global-state work usually targets library files first. If you can explain every step of this list without looking, you're ready to read and write global-state patches.

Where to go from here

  • Git's own documents: Documentation/MyFirstContribution.adoc, Documentation/SubmittingPatches and CodingGuidelines, plus General Microproject Information and Hacking Git.
  • C itself: The C Programming Language by Kernighan and Ritchie is short and still the best introduction. Modern C by Jens Gustedt is free online.
  • Shell: read t/README, which documents every test helper.
  • Read patches every day: pick one thread on lore that touches the_repository and read it from v1 to the final version. You'll learn what reviewers care about faster than any other way.
